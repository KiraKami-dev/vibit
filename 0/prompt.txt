## 1. What the platform docs say about architecture

- **Rejected in review:** a fixed click path with the model unused or only as a fallback, and a crawler that collects everything for one model call at the end. The model must choose where to go, what to search and which documents matter.

## 3. Options for the browser layer

**(a) Our own minimal loop on Playwright. Recommended.** The pinned Playwright 1.63 already has `page.aria_snapshot(mode="ai")`, the same ref-tagged snapshot that Playwright MCP uses. I tested it on the tender portal:
- 491 characters for the login page, taken in 0.02 s.
- Elements come tagged like `button "Anmelden" [ref=e10]`, and `page.locator("aria-ref=e10").click()` clicks them.

That gives us Playwright MCP's core with no Node process, no MCP layer and no extra dependencies. It works over CDP today, gives full control over which helpers exist (which matters for the code reviewer) and keeps prompts small and cacheable.

**(b) browser-use 0.13.11 (Python).** It supports `cdp_url` and an OpenAI-compatible `base_url`. Against it:
- A heavy dependency tree (Google API clients, a cloud SDK, telemetry) that would have to be disabled offline.
- Large system prompts and one action per step, which is slow for cost × time.
- It might fall back to launching its own browser, which the sandbox kills.
- Its built-in autonomous extraction is harder to defend in review.

**(c) Stagehand 4.2.0.** The TypeScript version needs Node ≥22.18 (fine) and supports a CDP URL and custom LLM clients. Its Python package is a client for a Stagehand server process (it depends on the Browserbase SDK), which is more moving parts in an offline sandbox. Its `act`/`extract` calls each add an LLM call, and switching to TypeScript costs us the kit. Not worth it.

**(d) Playwright MCP 0.0.83 or a pydantic-ai 2.55 agent.** Playwright MCP has `--cdp-endpoint`, but it adds a Node subprocess and about 25 verbose tool definitions; we get its snapshot format natively anyway. pydantic-ai would make a decent loop with OpenAI-compatible providers and typed output. It is optional, but a loop of about 150 lines is simpler to debug and to show to the reviewer.

**(e) Pixel / computer-use agents.** Slower and more expensive than the DOM. Keep screenshots only as a fallback tool for canvas or odd viewers.

## 4. Recommendation

- **Framework:** keep the starter kit (`run.py`, `browsers.py`, Python 3.12 + uv) and add our own tool loop. No agent framework.
- **Models:**
  - Qwen with thinking off for navigation steps.
  - Qwen with thinking on for decisions: which revision, approval or Q&amp;A applies.
  - Plain Python for arithmetic. The rules allow helpers to "calculate", and rules 4–27 are deterministic once the facts are chosen.
  - Keep `llm.py` provider-agnostic so a single environment variable can switch the decision step (or one stuck site) to a stronger model with a team key. Since quality ranks before cost × time, that is worth it only where Qwen measurably loses points in test runs.
  - Skip Clef in v1; it is an option later for quick yes/no checks.

**Module layout (`agent/`):**
- `agent.py`: the orchestrator. Reads the run, holds a shared store of findings with an asyncio event per fact, starts the site workers, watches the deadline and always submits by T−90 s.
- `llm.py`: the Qwen client, retry with backoff, a thinking on/off flag, usage logging, and stable system prompts as the cache prefix.
- `browser_tools.py`: the tools, all model-invoked:
  - **Snapshot and navigation:** `snapshot()` (AI aria snapshot, trimmed and including iframes), `goto(url)`, `back()`, `tabs()`, `switch_tab(i)`.
  - **Interaction:** `click(ref)`, `fill(ref, text)`, `select(ref, value)`, `press(key)`, `scroll(dir)`.
  - **Reading:** `read(ref|page)` for full text and tables, `open_document(ref)` for PDF/ZIP/iframe content, `next_page()` (paginates a result set the model chose), `screenshot()` as a fallback.
  - **Ending:** `finish(result)`, validated against a pydantic model.
  - **Generic auto-helpers:** login with the run's credentials when a login form appears, dismissing cookie walls, retrying error pages.
- `worker.py`: a generic loop of role prompt + goal + tools, with a step budget, a deadline, and up to 2 actions per turn where independent.
- `roles.py`: generic role prompts that describe what to find, not where to click: tender (reference, positions, Q&amp;A, configurator), spec (current revision, amendments), ERP (Kataloggruppe search, attributes, conditions, stock), mail (approvals, rule mails, TAN).
- `evidence.py`: pydantic records for each fact type. `calc.py`: half-up rounding, price scales, currency conversion, packaging, shared setup and project bonus allocation, with unit tests. `submit.py`: the tender worker fills the configurator from the calculated values, the mail worker fetches the TAN, then it signs.
- `agent.json`: `"browsers": 4`, `"models": ["qwen"]`.

**How the four browsers run:** tender starts first and publishes the reference and positions. Mail and spec start as soon as the reference is known. ERP starts as soon as each Kataloggruppe is known.

**Build order:**
1. **v1, in hours, gets an eligible signed bid:** one browser, the tender plus mail workers. Find the reference and positions, enter the bid with unfinished positions omitted, get the TAN, sign. This alone gives eligibility plus the reference and decision points.
2. **v2:** spec and ERP workers plus `calc.py` for material, quantity, base price, delivery and discount.
3. **v3:** clause rules (surcharge, packaging, shared setup, bonus, currency, metal indices), 4 parallel browsers, and a decision-model switch decided by test-run breakdowns.

  - "238,098 (en-US)" means 238098 per 100 ST, i.e. 2380.98 per piece.
- **Setup fee:** I found none anywhere in the ERP (no Rüst condition type, no field). It likely comes from mail or tender Q&amp;A.
- **Session timeout (idle):** ERP was still alive at 300 s and expired by 450 s. The supplier portal expired by 600 s. My 300 s probe there opened a fresh session that was still at the access gate, so it does not show whether the portal times out between 300 and 600 s. On expiry both redirect to `/login?returnTo=…` with "Sitzung abgelaufen", and you redo the login and gates.

## 3. Text vs vision
DOM and accessibility-tree text works, and is better than screenshots:
- A record-cover block fills the visible part of the ERP scroll regions, so screenshots of VK13 and Disposition show no data.
- Values sit in canvas `aria-label`s and CSS tooltips, which `aria_snapshot` misses.

The extractor must:
- resolve `aria-label`s on `role=img` and canvas elements
- include `role=tooltip` text
- drop `[hidden]` and `[aria-hidden=true]` elements
- strip zero-width spaces
- read iframes (the spec viewer).

There is no shadow DOM.

## 5. Suggested tools
**Model-driven actions:**
- `goto(url)`, `click(text or ref)`, `fill(field, value)`, `close_modal()` (the ×, never "Akzeptieren")
- `read_page()` and `read_frame()`, both through the cleaned extractor above
- `search_erp(q)`, where the model picks the query

**Safe deterministic helpers:**
- **Gates and recovery:** a `pass_gate()` per site (cookie, Belegnummer or Empfangsnummer form, slider). An `ensure_session()` that detects "Sitzung abgelaufen" or "Dienst vorübergehend nicht verfügbar", retries, re-logs in and returns to `returnTo`.
- **Reading selected items:**
  - `paginate(selected result set or spec revision)`
  - `read_material(material)` collecting the technical, planning, stock and every VK13 record with its scales for one model-chosen material
  - `parse_revision_history()` returning revision, normalised date and status
- **Parsing and maths:** a locale-aware number parser for the `(en-US)`/`(de-DE)` tags plus price-unit normalisation, a scale picker for a date and quantity, and calculators for FX, rounding, cartons and allocation.
