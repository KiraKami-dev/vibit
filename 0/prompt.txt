## 1. Flow of one record-kind search

**Planning**
- `plan_searches()` in `agent/research_mail.py:282-330` makes one model call with thinking off (`PLAN_TIMEOUT` 30 s, retries 3) and returns a `SearchPlan` of `PlannedSearch` items.
- Each item becomes a `Kind` (name, subject, sender, sender_form, site, what, schema; `:245-254`), chosen from the nine `SCHEMAS` (`:229-242`), deduped and sorted approval-first.
- It is called from `Orchestrator._plan_mail()` (`agent/orchestrator.py:702-722`): a quick try at 30 s per call within a 75 s budget, then a patient try at `PLAN_PATIENT_TIMEOUT` 90 s.
- `Orchestrator.mails()` (`:673-700`) starts the `MAIL_TABS` sign-ins, staggered 4 s apart (`_mail_tab`, `:724`), while the plan runs.

**Scheduling**
- `Orchestrator._research_mail()` (`orchestrator.py:745-812`) queues the kinds in the order approval, end_reserves, condition_rules, then the rest.
- Each tab loops: pop a kind, then `research_mail.research_kind(session, kind, reference, deadline=, seconds=budget)`.
- The budget comes from `_kind_seconds()` (`:728-734`): mail time left divided by rounds, clamped to 120–240 s.
- A kind that stopped with nothing is re-queued once if more than `MAIL_RETRY_SECONDS` (90 s) remain (`:789-796`).
- `research_mail.research_mail()` (`research_mail.py:887-917`) is a simpler copy of this loop, used only by the dev script.

**Per-kind goal prompt**: `_goal(kind, reference, again)` at `research_mail.py:333-346`.
```
Find every message on this website that is this record, for tender {reference}: {kind.what}
- Search for the exact reference {reference} together with the word {kind.subject!r}.
- Each time a result list shows hits whose subject is this record for exactly {reference}, call keep_results
  RIGHT AWAY with those exact subjects ... Older and newer versions share a subject; keep_results keeps all.
- If the hits span several pages, call collect_pages with the ref of the list's next-page control first.

As soon as every folder is checked, return a one-line summary. Do not open messages yourself, do not use back()
and do not note() anything: kept messages are read for you.
```
The first prompt is this goal plus the full current view, under the generic `worker.INSTRUCTIONS` (`worker.py:25-51`).

**Search worker**: `_search()` at `research_mail.py:499-541` calls `run_worker(session, goal, Summary, deadline=until, max_steps=20, thinking=True, grounded=False, tools=(paging_tool(Collected()), keep_messages_tool(kept)))`.

## 2. Existing mechanisms

- **(a) One search, classify hits for several kinds in one call:** none. `Kind`, `_goal`, `_Reading` and `read_message` are all single-kind.
- **(b) Reuse a result list across kinds:** not by design.
  - `Collected()` is created fresh per `_search`.
  - Incidentally, `keep_results` matches against `session.seen`, which persists per tab across kinds. A later kind on the same tab can keep a link an earlier kind's list showed, but the model is never shown those earlier lists.
  - Nothing is shared between tabs.
- **(c) Several messages in one model call:** none. It is one `read_message` per kept view; `gaps.reread()` (`agent/gaps.py:471`) also calls it per view.
- **(d) A kind with thinking off:** no flag. `thinking=True` is hard-coded at `research_mail.py:507` (search) and `:373` (reader). The plumbing exists (`run_worker(thinking=...)`, `llm.thinking("…", default)`), so it would be a one-line switch.

## 3. `collect_pages` and pagination helpers

**`paging_tool(collected, thorough=False)` → `collect_pages(next_ref)`** (`research_tender.py:307-371`) is the one mail uses.
- The model names the next/load-more control. The helper clicks it up to 40 times, polling up to 4 × 0.7 s per page, and stores each full page view in `Collected.pages`.
- It returns the whole list as concatenated full page views (`=== page view i` plus the entire view, folders and chrome included), capped at 30,000 chars.
- These are raw views, not compact rows.

**Context retention** (`worker._forget_old_views`, `worker.py:87-108`)
- Only the latest view-bearing message is kept in full; older ones shrink to stubs.
- The `collect_pages` result contains `URL:\nTitle:` headers, so it counts as the latest view.
- The `keep_results` return has no such header (`_heads` joins with " / "). So after collect → keep, the collected text of up to 30k chars is re-sent in full on every later request until the model navigates to another folder.
- `collect_pages` is not in `KEEP_RESULTS = {"search","collect","extract"}` (`worker.py:60`), so it is stubbed entirely once a newer view arrives.

**`site_tools.paginate` / `search` / `collect`** (`site_tools.py:288-485`) are not used by mail.
- They return compact numbered rows (`ROW_CHARS` 300, `MAX_ROWS` 200, `MAX_PAGES` 25) with link targets.
- Their results stay in context up to `KEEP_CHARS` 12,000.
- Note that `keep_results` only finds links in `session.seen` in the `[eN link "text" -&gt; href]` form, and `site_tools._format` rows use a different format (`["name" -&gt; href]`), though `paginate` does run every page through `session.look()`.

## 5. Why one worker per kind

No comment or doc line explicitly warns against merging kinds. The design is described rather than argued:
- `research_mail.py:5-7`: "Per kind a worker (one tab each) chooses its searches and folders; `collect_pages` pages through a result list it points at and `keep_results` opens the hits whose subject it names (only links it has actually seen)."
- `orchestrator.py:54-55`: "about nine record kinds took three rounds over four tabs ... six tabs take them in two rounds (tabs are free, the work and its cost stay the same)."

Relevant warnings in `docs/learned.md`:

- `:136-137` "One run with the mail kinds on site_tools.search/collect kept nothing in three kinds (150 s each; paging followed a message list into a session expiry); kept on the paging tool for now."
- `:122` "Mail kinds that find nothing burn the full 20-step budget (about 70 s per kind and tab)."
- `:246` "Step count times view size is the lever, not caching."
- `:258` "Mail search and mail readers are now about half the cost (42-55 %); the next cuts are there."
- `:156-160` gives the history of pipelined reads, the 60 s grace, the 45 s stall and reopen-on-redirect.

## Fair-play constraint

`CLAUDE.md:72-75`: "Must be agentic: a model chooses where to go, what to search and what matters. Rejected: a fixed click path ... or a crawler/helper that gathers all evidence before model-directed investigation. Allowed helpers: parse a page or document the model chose, paginate a model-selected result set, calculate, validate, retry, fill forms."

Helpers that rely on "paginate a model-selected result set":
- `collect_pages` (`research_tender.paging_tool`): the model names the next control.
- `site_tools.paginate`, `search` / `run_search` and `collect`: the model picks the field, query and list.

Helpers that rely on "parse a page the model chose":
- `keep_results` → `open_message`: the model names the subjects.
- `read_message`.
- `research_tender.keep_tool` / `open_and_keep`.

A related precedent is `AGENT_ERP_BATCH` (`research.py:864`, `learned.md:254`): the model's first ERP search is repeated by the harness for the other groups.

For a merged design, the model would still have to choose the query and folders and name which subjects belong to which kind. A helper that sweeps all folders for the reference before any model call is the rejected crawler pattern.

## Most promising cuts

1. **Multi-kind search worker** — `_goal()`, `_search()`, `keep_messages_tool()`, `_Reading` (`research_mail.py:333-541`) and the queue in `Orchestrator._research_mail()` (`orchestrator.py:745`).

### 4. Signing phase

Sequence after `FormReady`:
1. New sign worker: fresh look and a first model call with an uncached prompt.

3. `Mailbox._tan`: `revive()`, then `_goto(page.url)` reloads whatever page the mail tab last showed, then settle.
4. Mail worker: 3 requests, 10 s in your run.
5. Back in the sign model: fill the TAN, click submit, return the result.

In your run, 201 → 209 s is steps 1-3, 209 → 220 s is step 4, and 220 → 228 s is step 5.

## Techniques

| # | Technique | Published evidence | Our phase | Est. saved | Risk | Effort |
|---|---|---|---|---|---|---|

## What changed

**`agent/browser_tools.py`**
- **Request counting:** `Traffic` and `traffic_of(page)` are hooked in `_watch`. `Traffic.calm()` waits for 0.1 s with no request in flight, capped at 2.5 s. Event streams are not counted, and requests still open at the cap are forgotten so a long poll costs one settle, not every one.
- **Navigation:** a main-frame page load in flight is waited on for up to 15 s, beyond the 2.5 s cap. `_loaded` repeats the wait for every document that arrived meanwhile.
- **One probe:** `PROBE_JS`, `_probe` and `_work` replace the sweep. A plain page costs one script call; `_wait_answer` and `_collect_closed` are skipped when the probe answers and has nothing to report. If the probe fails or times out, the full sweep runs as before.
- **Human check:** the probe embeds `HUMAN_CHECK_JS` verbatim, so the main-frame check is found and solved in the probe call itself and cannot drift from the helper. Pages with child frames still call `_human_check`. After a solve the loop re-settles as today.
- **Effect waits:** `effect_mark(target)` and `effect(mark, cap, rest=False, ready=None)` are the one shared helper. `act` uses it with the 0.25 s cap.
- **`press`:** a page is not plain only when the probe finds a visible password field, cookie-notice buttons, a short text matching `ERROR_PAGE`, a solved human check, or child frames. Length alone no longer forces the full settle.
- **Stats:** `SETTLES` and `settle_table()` give one line per site (count, seconds, mean, slowest, settles where a helper acted). Each settle also writes a file-only trace event.
- **Off switch:** `SETTLE_FULL` is read once from `AGENT_SETTLE=full` and restores `networkidle`, the full sweep, the fixed sleeps and the old `press` test.

**`agent/submit.py`** — `fill_in` uses `effect` for the 0.15 s per-action wait (with `rest`) and the final 0.25 s.

**`agent/configurator.py`** — `choice_options`, `pick_option` and the typeahead branch use `effect` with `rest`. The combobox and typeahead waits also take `ready=` "options are listed", so they do not return before the suggestions render.

**`agent/agent.py`** — prints `===== page settles by site =====` after the model-call table.

**Tests**
- New `agent/tests/test_settle.py` (25 tests) covers (a) to (h), plus the human check in the main frame and in an iframe, an event stream, a scripted click onto a page that takes 3 s, and the probe-failure fallback.
- `tests/test_press.py`: the short-page case is split as you asked (short page takes the fast path; short page with error text gets the full settle).

## Not event-based, or unsure
