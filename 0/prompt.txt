## 2. Method for websites

There are three separate providers with different authority.

**A. Passive CDP attach** (`docs/browser-observation.md`, `src/browser/Cdp*.ts`)
- Input is a loopback CDP endpoint of a Chrome you started yourself with `--remote-debugging-port=9222 --user-data-dir=...`, plus a target ID.
- "This is a passive reverse-engineering capability, not a general browser automation or remote-control surface."
- "REA does not launch, own, or terminate this browser."
- It captures "DOM structure, accessibility nodes, scripts, resources, safe response/DOM metadata, attach-window network and console metadata, WebSocket frame sizes, workers, quota", with script sources and storage key names optional.
- It is deliberately value-free:
  - "DOM snapshots retain node types, node names, value lengths, and attribute names, but not text or attribute values."
  - JSON bodies, only with `--include-json-body-shapes`, are "converted immediately to complete value-free typed paths, types and observation counts, and discarded."
  - "Cookies and authorization headers are never retained."
- `analyze-web-bundle` statically parses scripts for "chunk edges, route and endpoint candidates, vendor fingerprints", with optional source-map fetching.
- `observe-web-execution` adds V8 precise coverage and request initiator stacks (`docs/web-runtime.md`).
- Coverage starts only at attach: "`prior_activity_available` is always `false`".

**B. Playwright scenario capture** (`docs/browser-scenario-contract.md`, `src/browser/Playwright*.ts`)
- Input is a declarative JSON scenario: a browser (launch with an executable path, or connect to loopback CDP), a `start_url`, and `actions` from a fixed vocabulary; the examples show `click`, `wait_for` and `wait_for_timeout`.
- Captures per step or at end: `dom`, `accessibility`, `url`, `screenshot`, `history`, `storage`, plus event families (`console`, `page-errors`, `network` and others).
- Network content is opt-in: `"capture": {"network": {"request_body": true, "response_body": true, "header_values": true}}`.
- "Captured bodies retain base64 bytes, byte count, media type, and SHA-256". This is the only web mode that keeps full response bodies.

**C. Offline capture inspection** (`docs/web-network-captures.md`, `src/browser/history/`, `bridge/mitmproxy/capture.py`)
- Input is a HAR 1.2 file, or a native mitmproxy flow file (needs mitmdump 12.2.3 on Linux).
- "This is an offline operation: recorded URLs are never fetched, and no browser or proxy listener is started."
- The output is "an inspection representation, not a reconstructed HAR file."

**Outputs.** Everything is a JSON "Evidence" record with provenance, coverage and limitations. `export-web-scripts` writes captured JavaScript to a directory for `analyze-javascript-application`. I found no OpenAPI output, spec generator or site cloner.

**Skill pack** (`.agents/skills/reverse-engineer-anything/SKILL.md`, version 37, plus `references/*.md`)
- It is routing and discipline guidance for an agent using the MCP tools.
- It tells the agent to pick the first tool by target type, work summary-first, and keep a finding ledger.
- "Every conclusion must distinguish observations, inferences, and unknowns."
- `references/runtime-observation.md`: "never claim REA clicked, navigated, evaluated page JavaScript, invoked IPC, captured prior activity, or contained the page's network."
- `docs/mcp-prompts.md` lists six MCP prompts (such as `investigate_feature` and `verify_reconstruction`); none is web-clone oriented.

## 6. Reusability for your four portals

**Useful**
- **Page structure:** `inspect-web-page` with `--include-accessibility-text --include-json-body-shapes --include-storage-keys` on a manually logged-in Chrome. You get the DOM/accessibility skeleton, form structure, and the XHR list with method, status, MIME type and value-free JSON shapes. Because it captures shape but not data, it suits simulators built on invented data.
- **Navigation flow:** `observe-web-session` over a 10–30 second window while you click through one flow, to get the ordered navigation and request sequence.
- **Route and endpoint candidates:** `analyze-web-bundle`, for any portal that is an SPA.
- **Simulator fidelity checks:** `capture-browser-scenario` against your local simulator (the docs' own examples target `http://127.0.0.1:3000`), with `compare-web-captures` and `compare-web-screenshots` to diff simulator against reference structure.
- **HAR route:** export a HAR from DevTools and run `inspect-web-network-capture ... har`. This keeps bodies, so handle it carefully.

**Not provided, so build yourselves**
- The simulator itself (Flask, Express or static HTML with invented data).
- Any OpenAPI or spec synthesis.
- Trap-case logic.
- Multi-page crawling: there is none, so each page or flow is one manual capture.

**Limitations for server-rendered portals**
- Default DOM capture drops text and attribute values, so for layout and labels you need the accessibility-text option or a scenario `dom` capture.
- Passive mode misses requests made before attach; reload after attaching.

**Is it worth it?** For four small portals, REA is heavyweight; Chrome DevTools HAR export or the claude-in-chrome `read_page` and `read_network_requests` tools give broadly the same raw material with less setup. REA's distinct value is value-free shape capture and capture diffing.

## D. Bid rules, answer schema, scoring, eligibility

rfq.md says "The brief states these rules in full." I summarised the rule text on the challenge page; I did not fetch the brief from the scouting endpoint, so it may carry more detail.

**The 29 rules**
1. **Quantity:** tender quantity, overridden by the latest clarification that changes that position.
2. **Requirement:** the position's requirement in the specification revision marked current.
3. **Material:** the active ERP material matching bore, stroke, pressure, mounting and certification exactly; if a position has none, the answer is no bid.
4. **Unit price:** the price condition valid on the scenario date, at the highest quantity scale reached, minus the approved discount, rounded half-up to the cent.
5. **Discount:** the most recent sales-director approval for this exact tender; otherwise 0 %.
6. **Lead time:** from-stock lead time when stock covers the quantity, otherwise production lead time.
7. **Total:** sum of quantity × unit price, rounded half-up to the cent.
8. **Decision:** bid with one entry per tender position; no bid with no positions and total 0 when a material is missing.
9. **Partial submission:** positions can be explicitly omitted (Position auslassen / Teilpunkte) and earn no position points; you must still sign and submit. A missing active material still requires no_bid; omission is not a substitute decision.
10. **Finding records:** the spec names a Kataloggruppe per requirement; search the ERP by group and compare attributes. Empty or over-broad searches list nothing; narrow to at most 20 results. Mail search ANDs words (tender reference plus topic); check inbox and archive.
11. **Agent requirement:** a model chooses navigation, searches and documents at run time; helpers may extract, parse, paginate, calculate, validate, retry and fill forms, but must not autonomously traverse the sites first.
12. **Commercial clauses:** Q&amp;A may assign a position to a Konditionsgruppe, resolved in the latest Konditionsregeln mail from kalkulation@ at the bidder mailbox domain for the exact reference. Its prose decides whether discount applies to base only, base plus mass surcharge, or neither. Setup fees are always excluded; the group overrides the default even for the same material; the default is base-only.
13. **Withdrawn answers:** a Q&amp;A answer may withdraw (zurückziehen) an earlier one by number; ignore its quantity change and use the latest remaining change, else the tender quantity.
14. **Scoped amendments:** after choosing the governing revision, apply Q&amp;A technical amendments naming that revision and requirement, only for the named attributes. Latest dated amendment wins per attribute; amendments to other revisions do not apply.
15. **Shared stock:** sum final quantities of all positions using the same material; stock must cover the whole sum or all use production delivery. No partial allocation; price scales stay per position.
16. **Conditional discount:** the latest exact-reference approval may require a minimum undiscounted net order value (final quantities × per-position scale prices, excluding mass surcharges and setup fees, half-up to cents). Threshold is inclusive; on failure use 0 % with no fallback to older approvals; for no_bid it yields 0 %.
17. **Units:** convert Satz using the governing spec's pieces per set; scales, inventory, allocation weights and bid quantities use final pieces. Carton rounding affects packaging cost only.
18. **Pricing breakdown:** `base_unit_price`, `surcharge_per_unit`, `packaging_per_unit`, `rebate_total` are optional with independent credit, all net EUR. The first three are per piece; `rebate_total` is for the whole position. Enter 0.00 for a known zero, blank for unanswered; do not feed rounded breakdowns back into the final formula.
19. The calculation rules apply to both practice and private datasets; missing calculation fields lose only their own points.
20. **Technical derivation:** for a requirement marked nutzbarer Weg, apply scoped amendments, then add twice the per-end reserve from the revision-specific Technikfreigabe, and match that nominal stroke in the ERP. Other attributes unchanged.
21. **Authority and time:** resolve each key from the latest record no later than the scenario date for the exact reference. Authorized subject/sender pairs: Technikfreigabe/technik, Verpackungstarife/logistik, Terminfreigabe/logistik, Devisenfixing/finanzen, Rüstpools/kalkulation, Projektbonus/finanzen. A newer record replaces the older; a failed quantity condition does not revive it; unrelated references and future-dated records never apply.
22. **Currency:** the valid condition names its currency and FX key. Normalize the price unit, pick the per-position scale, convert with EUR per currency unit, half-up to cents; that converted base price feeds all later calculations and thresholds.
23. **Packaging:** Q&amp;A assigns the tariff key; ERP gives pieces per carton. Charge ceil(final pieces / carton size) cartons per position; do not raise the bid quantity; packaging is not discounted.
24. **Delivery:** Q&amp;A assigns a commitment key; apply it only if its material matches and pooled final demand for that material is within its inclusive ceiling, else use shared-stock delivery. Commitments may differ by position for the same material.
25. **Shared setup:** Q&amp;A names pool members; ERP gives allocation mass (distinct from surcharge mass); the Rüstpools mail gives the single pool fee. Allocate by quantity × allocation mass using the mail's cent-allocation rule and add to the position's ordinary setup fee. `surcharge_per_unit` is before discount, excluding packaging and bonus.
26. **Project bonus:** the finance mail gives marginal percentage bands on the eligible undiscounted EUR goods total. Round the aggregate half-up, then allocate proportionally by largest remainders in cents (ties by ascending position id). `rebate_total` is the whole-position credit, zero for non-members, independent of discount clauses.
27. **Final price:** clause-discounted base + clause-discounted mass surcharge + (ordinary setup + allocated shared setup + carton cost − allocated project bonus) / final pieces. Use unrounded components, round half-up once; `total_net` is the sum of quantity × rounded unit price.
28. **Metal indices:** use the latest exact-reference Preisindizes mail from kalkulation@ at the bidder mailbox domain; if it lists validity windows, use the rate whose inclusive window contains the scenario date, not the last one listed.
29. **Scoring in bid cases:** see the weights below.

**Scoring weights (rule 29 and scoring.md)**
- **Bid case:** decision 5, tender reference 5, discount percent 5, total net 5, arithmetic consistency 5.

- **Positions:** 75 minus those checks, split evenly across positions. Within each: material 20 %, quantity 15 %, base price 15 %, surcharge 10 %, packaging 10 %, project bonus 10 %, final unit price 10 %, delivery/lead time 10 %.

- **Arithmetic (scoring.md):** defined as "every position, and a total that is their sum".

**Page view** (`extract.py` `WALK_JS`, 11-171)

**Model tools** (380-658)
- `goto(url)`: refuses any URL whose netloc differs from the site's (384). Each simulated site therefore needs its own host:port, and links must stay on it.

- Net effect: the usable-stroke path (rule 20) is being switched on end to end, and no_bid is made more conservative.

## 6. Dev scripts and where a simulator hooks in

- **`dev/run-local.sh`**:
  1. checks the proxy on `127.0.0.1:8765`;
  2. runs `eval "$(atira scout --env)"`;
  3. runs `cd agent &amp;&amp; HEADLESS=1 TRACE_DIR=agent/traces/&lt;utc stamp&gt; uv run --no-sync python agent.py`;
  4. runs `dev/track.py local --trace ...`, `track.py report` and `dashboard.py`.
- **`dev/track.py local`** (`summarise_trace`, 109-166) is not a scorer. It records requests, tokens, per-worker stats, errors and the `result` event (`submitted`, `confirmation`, omitted count) to `experiments/local-runs.jsonl`.
- **`dev/test-run.sh`**: runs `atira test-run ./agent --follow`, then `track.py platform &lt;run&gt;`. Real scoring exists only here.
- **`dev/smoke.py`**: one worker per site. `GOALS` is keyed by the public-1 siteIds `tender-portal`, `customer-portal`, `erp`, `mail` (31-36), so a simulator would have to reuse those ids or the script raises `KeyError`.
- **`dev/research_check.py`**: runs only `research()` and prints the `Findings` JSON. Parts are selectable; `RESEARCH_SECONDS` and `TRACE_DIR` apply. It is useful for per-trap checks against a sim without bid entry.
- **`dev/dashboard.py`**: platform runs only. Its `FIELDS` and `TOP` tuples (31-37) list the scored field names.

**What a "run against simulated portals" entry point needs**
1. Start four servers on distinct host:ports.
2. Export `CHALLENGE_SCOUTING` with the shape from section 1, after or instead of `atira scout --env`, keeping `QWEN_BASE_URL` and `QWEN_API_KEY`.
3. Run `agent.py` unchanged with `TRACE_DIR` set.
4. Read the signed bid from the simulator's own state. The agent returns nothing; the trace's `plan` event (`agent.py:161-165`) and `result` event (178) show intent only.
5. Diff the signed bid against the `calc.calculate` oracle, using the per-field weights in `docs/plan.md:131-133`.

**Things the sim must get right**
- Keep it outside `agent/`: fair play, and `atira test-run` uploads untracked files in the package directory.
- Run a scenario clock independent of wall time.
- A new TAN request invalidates the previous one; TAN mails get rising request numbers.
- Session expiry redirects to a login form.
